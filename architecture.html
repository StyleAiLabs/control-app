Layer 4 — Tenant Containers (One per customer · ports 4100–4199)

Each tenant gets an isolated Docker container. The provisioner creates a runtime/tenants/{id}/ directory with config, data, logs, and workspace folders, then starts the container pointing to that directory.

📁 runtime/{tenant-id}/
  • config/ — .env + metadata.json
  • data/ — persistent tenant data
  • logs/ — container logs
  • workspace/ — OpenClaw workspace
🔑 metadata.json
  • tenant_id (ULID)
  • business_name, slug
  • industry, skill_pack
  • assigned_port
  • workspace_url
⚡ Container lifecycle
  • Started by OpenClawProvisioner
  • Readiness: polls /readyz endpoint
  • Admin: start/stop via panel
  • Status in DB: Pending→Provisioning→Ready
⚠️ Current limit: 100 tenants
  • Ports 4100–4199 = 100 slots
  • All on single Docker host
  • Port range configurable in sync360.php
  • Nginx routing needed before launch

Actual Provisioning Flow — What Currently Happens
1
Customer fills out signup form
Provides name, email, password, phone, business name, industry. RegisterController creates a User record and a Tenant record (status: Pending), then queues a ProcessTenantProvisioning job.
POST /signup Http/Controllers/Auth/RegisterController.php
2
User is redirected to provisioning status page
The setup page polls GET /tenant/status every few seconds. It displays the current status (Pending → Provisioning → Ready) with a progress UI while the background job runs.
GET /tenant/setup → polls GET /tenant/status (JSON) tenant/setup.blade.php · TenantSetupController.php
3
Redis queue worker picks up the job
The dedicated worker container (start-worker.sh) is always running and listening on the Redis queue. It picks up ProcessTenantProvisioning and executes it asynchronously.
Redis queue → worker container → ProcessTenantProvisioning Jobs/ProcessTenantProvisioning.php · docker/start-worker.sh
4
TenantRuntimeService allocates a port and creates directory structure
Scans ports 4100–4199, finds the first unused one, assigns it to this tenant. Creates: runtime/tenants/{id}/config/, /data/, /logs/, /workspace/. Writes .env and metadata.json into /config/.
Port range: 4100–4199 · runtime/tenants/{ulid}/ Services/TenantRuntimeService.php
5
OpenClawProvisioner starts the Docker container
Uses Symfony Process to run docker-compose with the tenant's config. Mounts the runtime directory. Polls the /readyz endpoint on the assigned port until it responds 200. Updates tenant status to Ready with the workspace URL.
docker-compose → polls http://localhost:{port}/readyz Services/OpenClawProvisioner.php · Contracts/TenantProvisioner.php
6
Tenant marked Ready — customer sees workspace URL
DB updated: provisioning_status = Ready, workspace_url = http://localhost:{port}. The polling page detects the Ready status and redirects to workspace-ready page showing the URL.
tenant.provisioning_status = Ready · tenant.workspace_url tenant/workspace-ready.blade.php
7
⚠ MISSING: Stripe payment gate
Currently sign-up creates tenants for free. Before launch, a Stripe checkout step must be inserted between registration and provisioning. The Stripe webhook (payment_intent.succeeded) should trigger provisioning instead of the sign-up form directly.
Stripe → webhook → POST /webhooks/stripe → queue provisioning job
8
⚠ MISSING: Skill loading into container
The tenant's skill_pack is stored in the DB but no service yet loads those skills into the running container. This needs a Skill Deployer that fetches skill bundles from a registry and pushes them into the container after provisioning.
Skill Registry → Skill Deployer → container
9
⚠ MISSING: Channel connection (WhatsApp / email)
After the container is ready, the customer needs to connect their messaging channel. No onboarding wizard exists yet to guide them through WhatsApp Business API setup or email IMAP credentials.
Customer dashboard → channel connection wizard
